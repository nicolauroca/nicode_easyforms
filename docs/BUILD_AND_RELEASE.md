# Build and release

The current software version is `1.0.2`. The stable package is
`dist/pkg_nicode_easy_forms-1.0.2.zip`. Database acceptance covers MariaDB 11.4.5,
MySQL 8.4.8 and PostgreSQL 14.24 with Joomla 6.0.0. The user explicitly accepted
accessibility and waived the outstanding manual screen-reader check; no executed
screen-reader test or WCAG certification is claimed.

## Build the development package

From the repository root, with PHP and its ZIP, SimpleXML and JSON extensions:

```sh
php tools/build-development.php
php tests/build-package.php
```

The installable artifact is `build/development-package/pkg_nicode_easy_forms.zip`.
The directory also contains component, library, module, scheduler plugin and
extension plugin archives, `NOT_A_RELEASE.txt` and `build-manifest.json`. The
manifest records software version, every archive SHA-256 and each entry's byte
count and SHA-256. It explicitly records `release: false`.

The builder sorts source paths and fixes ZIP entry timestamps. After writing the
archives it verifies exact membership, bytes, timestamps, bundled GPL license,
child/package version agreement and the nested package bytes against their
standalone archives. It does not extract or execute archive contents. Unexpected,
duplicate, missing or changed entries fail verification; symlink sources are
rejected. Files under build, tests, docs, local credentials and databases are not
package inputs. Sources under the five extension directories are package inputs.

The reproducibility test runs the builder twice in the current toolchain and
requires identical hashes and entry inventories. It also corrupts separate copies
to verify rejection of additional, changed and missing entries. Its result is
`build/package-reproducibility-results.json`; diagnostic copies remain under
ignored `build/package-audit-*`. Matching builds on this toolchain do not establish
identical compressed bytes across different PHP/libzip/zlib versions or operating
systems. Record and verify the release toolchain before a production release.

## Isolated installation

The development artifact can be installed through Joomla's extension installer.
The repository's configured disposable integration site supports:

```sh
php build/joomla-6.0.0/cli/joomla.php extension:install --path=ABSOLUTE_PATH_TO_PACKAGE --no-interaction
```

Use the absolute path to the generated package. This updates all packaged child
extensions. Development acceptance must use isolated fixtures, not user production
data. Native clean installation, update and uninstall tests are documented in
`docs/TESTING_GUIDE.md`.

## Release gates

The full contract is `docs/22_RELEASE_SPEC.md`. All 133 requirements and the
cross-feature acceptance scenario must be verified before declaring completion.
Compatibility, security, accessibility, scale, migration and lifecycle checks,
release versioning and final documentation remain independent gates. Generating
an archive or passing its integrity audit does not satisfy those gates. A final
versioned artifact under dist is not generated by this development command.

## Final versioned package

Once every requirement except OPS-008 is COMPLETE, set the same stable SemVer
version in all six extension/package manifests, update the changelog and run:

```sh
php tools/status.php --check
php tests/build-package.php
php tools/build-release.php
```

The release builder reuses the audited source packaging path, rejects unfinished
product acceptance and development versions, and writes the versioned ZIP,
SHA-256 sidecar and source inventory/toolchain report under `dist`. It refuses
to replace a different artifact with the same version. Installation and the
cross-feature acceptance must then be verified against that exact ZIP before
closing OPS-008. Accessibility acceptance for 1.0.0 was explicitly granted by
the user on 2026-09-28. There is no supported previous stable EasyForms release to migrate
from; existing evidence covers clean install and the pre-release upgrade path.

The requested forty-step scenario is `tests/product-acceptance.php`. In the
configured isolated Joomla fixture, start its nonce-protected loopback router:

```sh
php -S 127.0.0.1:13407 -t build/joomla-6.0.0 tests/http/product-router.php
```

In another terminal, run `php tests/product-acceptance.php PATH_TO_PACKAGE.zip`.
The default package is the development ZIP. The scenario installs that exact
artifact, authors one form through authenticated administrator routes, creates
a native menu and modules, and verifies all forty requested steps. It injects a
Joomla test CAPTCHA provider and captures prepared MIME without external delivery.
Its report records the package hash and each step in
`build/product-acceptance-results.json`. It unpublishes its form/menu/modules
afterward; unrelated native jobs are left untouched. Stop the test router when
finished. These fixture commands must not target a production installation.
